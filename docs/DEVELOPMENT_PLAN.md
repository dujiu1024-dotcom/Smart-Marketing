# AI 门店运营官 — 开发实施计划

> 计划版本：1.0  
> 制定日期：2026-11-10  
> 产品基线：v1.8  
> 适用仓库：`dujiu1024-dotcom/Smart-Marketing`  
> 状态：建议执行基线；技术选型和关键外部依赖完成确认后进入正式开发

## 1. 执行摘要

本计划以现行《项目宪法》《产品设计基线》《UI/UX 基线》《Demo 验收矩阵》《技术架构》和《IterWave 可复用能力审查》为依据。

开发目标不是继续扩展 Demo 页面，而是把现有 Demo 所定义的体验和业务流程，逐步实现为真实可运行、可恢复、可审计、可验证经营效果的产品。

**实施策略：先验收并冻结 Demo，再建立生产底座；先打通一个完整真实营销闭环，再扩展渠道；经营效果必须以可追溯数据为依据。**

首期采用模块化单体 + 独立异步 Worker + AI/渠道 Provider，不采用全面微服务；不引入 n8n 作为核心流程引擎，也不把 ComfyUI 作为首期硬依赖。

## 2. 开发约束

### 2.1 产品范围

必须遵守：
- 产品定位：AI 门店运营官；按需制作；完整营销执行官；以可验证经营效果为核心壁垒。
- 商家只负责提出目标、确认经营事实、审核交付物和确认发布。
- 文案审核、图片审核是两个独立状态机。
- 策略/事实/内容变更必须产生新版本，并按依赖关系使下游结果失效。
- 发布成功必须有外部平台响应或可核验凭证；结果不确定时转人工核实。
- 经营效果独立于营销任务；没有数据时显示空态、采集中或明确标记的样例。
- 门店经营资料由门店端维护；平台后台只承担平台管理职责。

禁止范围蔓延：ERP、POS、CRM、广告投放/预算管理、通用工作流编排器、自动评论/关注/私信、复杂排期和自动循环营销均不属于本期开发范围。

### 2.2 Demo 对齐

- Demo 是页面结构、导航层级、交互和状态反馈的验收基准。
- 开发前必须运行 Demo 并实际走查对应页面。
- 独立二级页面不得擅自改为弹窗或同页展开。
- 不得用静态卡片、假按钮或固定结果替代真实业务行为。
- Demo 模拟与生产能力必须明确区分。

### 2.3 技术架构

- 业务核心：模块化单体。
- 执行层：独立异步 Worker，任务状态持久化。
- 数据：PostgreSQL 作为业务事实主库。
- 媒体：S3 兼容对象存储。
- AI：Text / Image / Vision / OCR Provider 抽象。
- 渠道：独立 Channel Adapter，逐项声明授权、读取、草稿、发布和指标能力。
- 可靠性：幂等、租约、重试边界、死信/人工恢复、Outbox、审计和可观测性。
- 不因模块数量拆分微服务；只有出现独立扩缩容、故障隔离或部署收益时才评估拆分。

## 3. 当前基线与主要缺口

截至 2026-11-10，仓库当前为前端交互 Demo：
- 页面入口为 `demo/index.html`，使用原生 JavaScript ES Modules。
- 页面状态和数据主要由浏览器 localStorage 保存。
- 已有任务、门店资料、经营效果、管理端等页面渲染模块。
- 需求/策略门控、文案/图片审核路径和发布前检查已有部分本地逻辑。
- 真实模型、图像生成、OAuth、官方渠道发布、服务端权限、持久化任务队列和真实经营数据尚未接入。
- 验收矩阵明确：真实浏览器 E2E 尚未完成，不能宣称 Demo 正式验收通过。

当前文档体系已明确产品、体验、架构与复用方向，但仍缺少可执行开发计划，以及需要进一步固化的技术选型、API 契约、数据模型和测试计划。

## 4. 分阶段路线图

阶段顺序是强依赖关系；不得跳过前置验收直接进入后续阶段。

| 阶段 | 优先级 | 目标 | 主要交付 | 退出条件 |
|---|---|---|---|---|
| 0. Demo 验收与范围冻结 | P0 | 确认目标产品行为 | 浏览器验收报告、缺陷清单、冻结版 Demo | 核心路径及关键异常路径有真实浏览器证据 |
| 1. 技术选型与工程骨架 | P0 | 形成可执行技术基线 | 技术选型文档、项目骨架、CI、环境配置 | 技术决策获确认，能构建、测试、启动 |
| 2. 生产数据与权限底座 | P0 | 建立可信业务事实 | 认证、Store/StoreUser、PostgreSQL、迁移、对象存储 | 门店数据服务端隔离测试通过 |
| 3. 营销核心领域闭环 | P0 | 实现真实任务和审核流程 | 状态机、策略快照、文案/图片版本、审核、质检、发布包 | 一次营销任务可完整创建、修改、审核、冻结和恢复 |
| 4. AI 与媒体执行能力 | P0 | 用真实 Provider 替换模拟能力 | AI Gateway、文本生成/整改、图片生成/编辑、OCR/质检 | 真实调用成功/失败/超时均可追踪，结果版本可回溯 |
| 5. 渠道与热点接入 | P1 | 建立真实外部执行能力 | 热点 Adapter、渠道账号授权、草稿保存、状态读回、受控发布 | 至少一个目标渠道通过真实授权与草稿/发布联调；其他渠道状态如实标记 |
| 6. 经营效果与数据证据 | P2 | 建立经营效果验证能力 | 指标观测、来源口径、观察窗口、归因证据和建议 | 内容表现与经营结果分层展示，归因有数据来源和可信度 |

说明：P0/P1/P2 是功能优先级；阶段 7 是所有功能上线前的强制质量门禁，不代表它低于 P2。

## 5. 阶段任务分解

### 阶段 0：Demo 验收与范围冻结

**目标：确认开发团队实现的是同一个产品，而不是根据静态页面自行猜测。**

任务：
1. 在本地按 README 启动 Demo。
2. 对门店端和管理端逐页走查：入口、路由、二级页面、表单、审核、返回、空态、错误态和状态反馈。
3. 按产品流程执行完整演练：按需制作、热点采纳/跳过、策略确认、文案审核/整改、图片审核/整改、渠道适配、质检、发布确认。
4. 检查版本变化、下游失效、刷新恢复、异常输入和数据持久化。
5. 在 1440、1280、1024、768、390 等视口检查关键页面。
6. 将验收矩阵中的“代码已实现”与“浏览器实测通过”分开记录。
7. 修复阻断核心流程的 P0 Demo 缺陷；不在此阶段增加产品范围。

交付：
- Demo 浏览器验收记录（含环境、步骤、结果和截图）。
- P0/P1/P2 缺陷列表。
- 经确认的页面/交互基线。

退出条件：
- 核心营销流程无阻断缺陷。
- 关键页面层级、交互和状态有浏览器实测证据。
- Demo 模拟边界清楚。
- 产品范围和页面结构冻结。

### 阶段 1：技术选型与工程骨架

**目标：一次性确定首期工程栈，避免开发中途反复换框架。**

必须形成正式决策的项目：
- Web 前端框架与组件/样式方案。
- 后端 API 框架、语言和项目结构。
- ORM、数据库迁移工具。
- PostgreSQL 部署与连接池策略。
- 持久化队列/Broker、Worker 执行框架。
- 对象存储及本地开发替代方案。
- 身份认证与门店权限实现。
- 单元、集成、浏览器 E2E 测试工具。
- CI、容器化、部署与日志/监控方案。

工程任务：
1. 建立统一代码仓库目录与开发环境。
2. 配置格式化、Lint、类型检查、单元测试和构建流水线。
3. 建立开发、测试、生产环境变量规范。
4. 建立 API 版本、错误响应、分页、幂等和日志规范。
5. 固化数据库迁移与测试数据生成流程。

交付：
- `docs/TECH_STACK_SELECTION.md`。
- 工程目录与运行说明。
- CI 工作流和最小健康检查接口。

退出条件：
- 新成员按文档可独立启动项目。
- CI 能完成静态检查、测试和构建。
- 技术选型不存在未决的核心基础设施问题。

### 阶段 2：生产数据与权限底座

**目标：先保证数据归属和资产安全，再接入 AI。**

开发顺序：
1. Identity：登录、Session、认证主体。
2. Store：门店、StoreUser、门店归属和访问策略。
3. Store Knowledge：门店档案、商品服务、活动优惠、品牌规范、客群、知识库。
4. Asset：素材上传、对象存储、签名 URL、哈希和版本元数据。
5. Database：迁移、索引、约束、审计字段和测试数据。

强制规则：
- 所有门店业务数据带 `store_id`。
- 服务端从认证主体解析门店权限，不信任前端传入的 `store_id`。
- 未知数据保持 NULL，不以 0 代替。
- 金额使用明确币种和 Decimal。
- 原始图片不可覆盖；编辑结果作为新资产。
- 密钥只保存安全引用，不保存明文，不下发浏览器。

退出条件：
- 门店 A 无法读取、修改门店 B 的任何业务数据和文件。
- 权限测试覆盖列表、详情、文件、任务和 API 参数篡改。
- 数据迁移可重复部署、可回滚或有明确前向修复策略。

### 阶段 3：营销核心领域闭环

**目标：让固定营销流程成为真实后端业务，而不是前端按钮控制。**

建议实现顺序：
1. MarketingTask 与任务类型。
2. 需求理解结果、经营事实确认和策略快照。
3. 领域状态机、步骤门槛、跳过原因和流程恢复。
4. CopyArtifact、不可变文案版本和独立审核状态机。
5. MediaAsset、图片产物版本和独立审核状态机。
6. ChannelContent、渠道适配结果和依赖指纹。
7. QualityReport、质检规则和质检新鲜度。
8. PublishPackage 冻结、商家确认、发布幂等门槛。
9. ReviewRecord、TaskEvent、AuditEvent。

必须覆盖：
- 需求/策略变化只使受影响的下游产物失效。
- 文案整改不重置无关图片；图片整改不重置已通过文案。
- 审核意见绑定具体版本。
- 不适用步骤必须记录跳过原因、操作者和时间。
- 未审核、未质检、未最终确认不得进入正式发布动作。
- 营销任务状态与底层 Job 状态分离。

退出条件：
- 后端状态机可独立测试。
- 关键状态不能通过直接调用 API 绕过。
- 任务刷新、重复提交、并发修改和失败恢复均有自动化测试。

### 阶段 4：AI 与媒体执行能力

**目标：把 Demo 模拟产出替换成可配置、可审计的真实 AI 能力。**

任务：
1. AI Gateway：统一模型配置、路由、超时、重试、限流和费用记录。
2. TextProvider：需求理解、策略建议、文案生成、段落改写和整改。
3. ImageProvider：直接生成信息图、原图二次改造、多版本输出。
4. Vision/OCR：图片文字识别、商品事实核对、画面和尺寸检查。
5. Prompt 管理：业态模板、变量 Schema、版本、草稿、发布和回滚。
6. Job Runtime：持久化队列、Worker、进度、租约、心跳、幂等、重试和人工恢复。
7. 记录 provider、model、prompt_version、请求 ID、耗时、费用、状态和脱敏错误。

安全要求：
- 模型输出必须结构校验并进行业务事实校验。
- AI 不得创造价格、库存、优惠有效期、地址和营业时间。
- 图片编辑必须保留原图、来源和指令。
- Provider 失败时明确显示失败，不回退为伪造的成功结果。

退出条件：
- 文本和图片至少各有一条真实 Provider 链路。
- 超时、限流、无效输出和服务不可用有明确状态及恢复路径。
- AI 调用可以按门店、任务、模型和 Prompt 版本审计。

### 阶段 5：渠道与热点接入

**目标：从内容交付走向可核验的渠道执行。**

任务：
1. 定义统一 Channel Adapter 契约和平台能力矩阵。
2. 先实现授权、Token 刷新、撤销、健康检查和能力探测。
3. 接入热点来源，记录原始来源、发布时间、采集时间、去重键和证据。
4. 完成热点与门店业态、商品、客群和营销目标匹配。
5. 完成各渠道内容字段映射、预览和规则校验。
6. 实现草稿保存与读回核验。
7. 对已验证平台开放受控发布；发布前必须冻结发布包并取得商家确认。
8. 采集平台作品 ID、URL、账号 ID、发布时间和外部响应证据。
9. 建立限流、熔断、登录失效、验证码和人工恢复路径。

实施策略：
- 先选择一个有可用官方授权/API 条件的渠道做端到端试点。
- 其余目标平台保留 Adapter 契约和能力状态，不得把未验证能力展示为已接通。
- 页面自动化只作为经规则、安全和账号风险评估后的备选方案。

退出条件：
- 至少一个渠道真实完成授权、草稿保存、状态读回及可核验发布结果。
- 其他平台有明确 supported / unsupported / pending_verification 状态。
- 不确定的外部操作不会被误报成功或自动重复执行。

### 阶段 6：经营效果与数据证据

**目标：形成真正区别于普通 AI 内容工具的经营反馈能力。**

任务：
1. 建立 MetricObservation：指标值、来源、采集时间、统计周期、定义、状态和完整性。
2. 区分内容表现指标、互动/意向指标、到店/订单/核销/销售指标。
3. 建立作品与营销任务、发布包、平台账号的可信关联。
4. 建立观察窗口，避免发布后立即生成效果结论。
5. 接入当前能够合法、可靠获得的交易/核销数据源。
6. 建立 AttributionEvidence：归因依据、样本量、置信度和限制。
7. 输出渠道、主题、时段、素材和 CTA 的分层洞察。
8. 将结果转为下一次按需制作建议；不得未经商家发起自动创建营销任务。

退出条件：
- 所有指标可追溯来源、口径、周期和更新时间。
- 未知指标保留 NULL。
- 无交易证据时不输出 ROI、销售增长或到店增长结论。
- 样本不足时明确显示“数据积累中”。

### 阶段 7：上线准备与质量加固

任务：
- API 鉴权、门店越权、密钥、上传文件和日志脱敏安全审查。
- 核心流程单元、集成和 E2E 回归。
- Worker 崩溃、队列堆积、重复投递、供应商故障和外部状态不确定演练。
- 数据库备份、恢复演练、对象存储生命周期与访问策略检查。
- 结构化日志、链路追踪、成本监控和告警。
- 桌面/移动端视觉回归、键盘操作和可访问性检查。
- 部署、回滚、密钥轮换、故障排查和运营手册。

退出条件：
- 所有 P0 验收项通过。
- 无未处理的严重安全问题。
- 核心任务能够在服务重启后恢复或安全进入人工处理。
- 未接入平台能力和数据限制在产品内明确披露。

## 7. 建议的 MVP 验收范围

MVP 不以页面数量或平台数量作为完成标准，以一个真实端到端营销闭环作为完成标准。

必须具备：
- 一个门店真实登录和服务端门店权限隔离。
- 门店经营资料、商品、活动、品牌规范和素材可维护。
- 商家按需提出目标，AI 读取真实门店上下文。
- AI 真实生成策略和文案，支持修改、版本与独立审核。
- AI 真实生成或编辑图片，支持原图保护、版本与独立审核。
- 渠道适配、质检、发布包冻结和商家最终确认。
- 至少一个渠道真实授权和可核验草稿/发布链路。
- 任务、Job、AI 调用和外部操作可追溯、可恢复。
- 经营效果页面真实区分内容表现与经营结果；缺失数据不伪造。

四个平台的目标体验和 Adapter 能力边界仍需在产品基线内保持一致，但生产启用应按官方接口、授权和实测结果逐个平台开放。

## 8. 测试与质量门禁

| 层级 | 必测内容 | 合并/发布门禁 |
|---|---|---|
| 单元测试 | 状态机、版本失效、事实校验、权限策略、幂等键、指标 NULL 语义 | 必须通过 |
| 集成测试 | 数据库迁移、API、对象存储、队列、Worker、Provider Mock | 必须通过 |
| 安全测试 | 门店越权、IDOR、密钥泄露、文件访问、Prompt/日志脱敏 | P0 必须通过 |
| 浏览器 E2E | 从需求到发布确认、审核整改、返回/刷新、异常状态 | 核心路径必须通过 |
| 外部联调 | OAuth、草稿保存、发布结果读回、指标同步 | 启用对应平台前必须通过 |
| 视觉回归 | 1440 / 1280 / 1024 / 768 / 390 关键页面 | 发布前必须通过 |
| 恢复演练 | Worker 重启、重复任务、超时、失败、外部结果未知 | 发布前必须通过 |

任何未执行测试都必须明确标记“未执行”；静态检查不得替代浏览器验收；Mock 测试不得替代真实平台联调。

## 9. 主要风险与前置决策

| 风险/待决策 | 影响 | 处理要求 |
|---|---|---|
| 技术栈未形成独立选型文档 | 工程实现可能分叉 | 阶段 1 形成正式选型并获确认 |
| Demo 未完成真实浏览器验收 | 开发对目标体验理解不一致 | 阶段 0 先完成核心流程和异常路径验收 |
| 平台官方 API/OAuth 权限不确定 | 影响自动草稿、发布和指标读取 | 尽早核查平台开放能力，按能力矩阵逐项启用 |
| 门店经营数据来源不确定 | 影响经营归因壁垒 | 先建立指标证据模型，再确定可接数据源 |
| AI 图片生成成本和质量波动 | 影响毛利、用户体验和审核成本 | Provider 可替换，建立费用/质量记录与失败兜底 |
| IterWave 代码复用许可证及耦合风险 | 影响合规与维护 | 优先复用设计模式；复制代码前逐文件检查 LICENSE/NOTICE 和依赖 |
| 一次性建设过多模块 | 延迟真实闭环 | 按一个门店、一个完整任务、一个真实渠道逐步验证 |

## 10. 项目执行与变更纪律

每个开发任务必须包含：
- 对应产品需求/验收矩阵 ID。
- 用户路径和对应 Demo 页面。
- 业务规则、状态变化和失败恢复。

- 单元/集成/E2E 验收标准。

5. 下一阶段进入条件。

产品范围、页面职责、核心流程、技术栈、数据模型或外部依赖发生变化时，必须走项目宪法规定的决策与文档同步流程。
