# AI 门店运营官 — 开源框架选型与复用建议

> 文档版本：1.1  
> 日期：2026-11-10  
> 适用产品基线：`docs/PRODUCT_DESIGN.md` v1.8  
> 目标仓库：`dujiu1024-dotcom/Smart-Marketing`  
> 研究范围：Smart-Marketing 与 IterWave Content Ops 两个自有仓库，以及相关开源框架  
> 状态：技术选型建议，尚非已实施架构

## 1. 结论摘要

**建议采用“自有确定性业务状态机 + FastAPI 服务层 + React 前端 + 独立媒体/渠道适配器”的轻量架构。首期不引入 n8n 和 ComfyUI；LangGraph 也不是必选项，满足复杂执行编排条件后再引入。**

不建议把产品整体改造成 Dify、n8n 或其他通用 Agent 平台。AI 门店运营官的差异化不在于提供一个可视化工作流编辑器，而在于：商家用一句话提出经营目标，系统能可靠地完成策略、文案、图片、渠道适配、质检、人工确认与发布准备，并在数据可用后验证经营结果。

### 1.1 推荐技术决策\n\n本项目是固定业务流程的 AI 产品，不是让用户自由搭建流程的自动化平台。技术选型以“业务状态由自有代码控制、AI 只处理需要智能判断的环节、媒体能力通过适配器接入”为原则。图像生成是产品必需能力，但 ComfyUI 不是必需组件；同理，营销流程需要可靠状态管理，但不代表首期必须引入 LangGraph。

| 能力层 | 推荐方案 | 决策 | 原因 |
|---|---|---|---|
| 门店产品前端 | React + TypeScript（现有 Demo 逐步演进） | 沿用 | 保留已经收敛的商家交互，不引入通用工作流画布 |
| API 服务 | FastAPI | 沿用 | IterWave 已有实践，适合 Python AI 服务与异步 API |
| 数据模型/校验 | Pydantic v2 | 沿用 | 约束模型输出、API 请求、业务对象与工具参数 |
| 核心业务流程 | 自有 Python 业务状态机/服务层 | **首期必选** | 固定流程由产品自身掌控，业务状态、规则、审核门控和幂等逻辑必须确定、可测试、可审计 |\n| AI 子流程编排 | 普通 Python 函数；复杂时评估 LangGraph | **按需引入** | 首期不为固定流程额外增加 Agent runtime；出现复杂分支、checkpoint、长时运行和人工中断恢复需求时再引入 |
| Agent 单元 | LangGraph 节点内封装模型/工具；必要时评估 PydanticAI | 组合 | 先保持一个执行框架，避免两套 Agent runtime 争夺状态 |
| 图像生成与编辑 | 统一 Image Provider Adapter + 云端图像模型 API | **首期必需能力；不需要 ComfyUI** | 产品必须具备生图/改图，但不需要先自建节点式工作流引擎；保持 Provider 可替换 |
| 浏览器自动化 | Playwright | 沿用并收紧边界 | 可用于 E2E、只读采集、平台草稿准备；真实发布须遵循授权与人工确认边界 |
| 任务调度/队列 | 现有 APScheduler 仅用于单实例轻量调度；生产评估持久化队列/工作流引擎 | 分阶段 | 不能将单进程调度器误当作可靠分布式任务系统 |
| 数据库 | MVP 可延续 SQLite；多门店生产优先 PostgreSQL | 分阶段 | 生产需要事务、并发、权限隔离、审计与迁移管理 |
| 文件/素材 | 对象存储 + 元数据数据库 | 生产必需 | 原图、生成版本、渠道内容包需要可追溯、不可覆盖 |
| 自动化集成 | 自有后端服务/API Adapter | **首期不引入 n8n** | 当前是固定、受控的产品流程；直接由后端调用外部 API，避免额外工作流配置、状态同步和运维面 |
| 可视化 AI 平台 | Dify（可选实验/提示词原型） | 不作为核心 runtime | 与自有业务流程重复，且需单独评估其附加许可证条件 |

## 2. 两个自有仓库的可复用资产

### 2.1 Smart-Marketing

当前仓库定位是 AI 门店运营官前端交互 Demo，产品基线 v1.8 已明确：

- 按需制作、AI 完整执行、商家确认关键事实和发布动作。
- 文案审核与图片审核独立，整改形成新版本。
- 图片生产包含直接生成信息图、商家原图二次改造、自有图片上传。
- 渠道适配、质量检查、发布确认是明确的业务阶段。
- 营销任务与经营效果分离；无真实数据时不得伪造效果。
- 门店资料、账号运营监测、经营效果和平台管理端具有明确边界。

**应复用：** 产品流程、页面交互、业务术语、状态与审核规则、内容版本概念、质量检查项、验收矩阵。

**不应误认为已具备：** 真实 LLM、真实生图/改图、实时热点、OAuth、真实平台发布、官方数据同步、生产级认证与门店隔离。当前仓库 README 已明确这些属于生产接入缺口。

### 2.2 IterWave Content Ops

其 README 描述的现有技术栈：

- Python 3.11+、FastAPI、Pydantic v2。
- SQLite 与版本化 schema migration。
- APScheduler、全局任务队列、隔离 worker。
- Playwright 浏览器自动化。
- React 18、TypeScript、Vite。
- Pillow、OpenCV、NumPy 图像处理。
- 平台适配器、任务状态、计划版本、恢复与分析等模块。

**建议优先抽取的工程能力：**

1. FastAPI 路由、应用生命周期、配置管理和 Pydantic Schema 组织方式。
2. 任务队列、worker 隔离、超时、失败记录与恢复机制。
3. 数据库 migration、任务/计划版本管理。
4. Playwright 封装与平台 Adapter 分层。
5. Pillow/OpenCV 的图片尺寸、格式、压缩、裁切和基础质量处理。
6. 测试结构、配置模板、密钥不入库、安全部署约束。

**需要调整后复用：**

- IterWave 的内容计划/子计划概念可映射为内部营销执行计划，但不能原样暴露给门店商家。
- 其“人工确认发布”边界与本产品 v1.8 一致；自动化应优先做到草稿准备、状态回读和证据留存。
- SQLite、单进程 APScheduler 和单 worker 约束只适合当前部署规模，不能直接视为多租户生产方案。
- IterWave 现有平台适配代码包含基于 Easel 的派生代码，复用时必须保留 Apache-2.0 的 LICENSE/NOTICE 归属要求，并逐文件核验来源。

## 3. 候选开源框架比较

### 3.1 AI Agent 与工作流编排\n\n**首期决策：不把 LangGraph 作为必选依赖。** 我们的营销流程相对固定，需求理解、策略、文案、图片、审核、质检和发布准备等阶段由产品定义，不需要让商家配置任意工作流。首期用 Python 服务函数和显式业务状态机即可实现；模型只参与策略分析、文案生成、图片提示词/编辑指令生成等需要智能判断的步骤。价格校验、活动有效性、权限、审核状态、版本关系、任务流转和发布门控必须由确定性业务代码执行。

| 项目 | GitHub | 适用点 | 对本项目判断 |
|---|---|---|---|
| LangGraph | https://github.com/langchain-ai/langgraph | 有状态图编排、持久化、暂停/恢复、人工介入、流式事件 | **首选核心执行 runtime** |
| PydanticAI | https://github.com/pydantic/pydantic-ai | 类型安全 Agent、结构化输出、模型供应商切换、评估能力 | 可作为 Agent 单元备选；首期不与 LangGraph 并行承担总编排 |
| CrewAI | https://github.com/crewAIInc/crewAI | 角色/团队式多 Agent 协作 | 当前业务流程更需要确定性状态与审批门控，非首选 |
| Dify | https://github.com/langgenius/dify | 可视化 LLM 工作流、模型管理、RAG、Prompt 调试 | 可用于原型实验，不建议承载产品核心业务状态 |
| n8n | https://github.com/n8n-io/n8n | 大量 SaaS/API 集成、事件触发与自动化 | 外围集成工具，不是 AI 营销执行主引擎 |

**何时再引入 LangGraph：**

营销执行不是单轮问答，而是一个长流程：需求理解 → 经营上下文 → 策略确认 → 文案生成与审核 → 图片生成与审核 → 渠道适配 → 质检 → 最终确认 → 发布准备。过程中会暂停等待商家审核，也可能因修改意见回到某个阶段；服务中断后必须能恢复到正确状态。

LangGraph 的定位是低层、有状态的 Agent 编排 runtime，支持确定性节点与模型驱动节点混合、持久化 checkpoint、人工介入与流式更新。它不强制采用特定 Prompt 或 Agent 结构，适合把产品自己的业务规则保留在应用层。

参考：
- https://github.com/langchain-ai/langgraph
- https://docs.langchain.com/oss/python/langgraph/
- 项目 README 标注 MIT License；正式采用前仍应锁定依赖版本并复核发行包许可证。

**为什么不直接用 Dify：**

Dify 的可视化 Workflow、模型管理、RAG 和 Prompt IDE 很适合快速验证模型链路。但本项目已经有自己的商家产品界面、审核机制、营销任务与经营效果边界。把 Dify 当核心 runtime 会增加一套工作流定义、执行状态、权限和发布治理体系，可能造成业务状态双写和产品边界模糊。其仓库许可证为 Dify Open Source License（基于 Apache 2.0 并附加条件），商业化部署前必须进行许可证审查。

参考：https://github.com/langgenius/dify

**PydanticAI 的位置：**

适合结构化产出要求高的独立 Agent，例如商品事实提取、营销策略 JSON、文案结构、质检报告和经营归因输入。当前首期可以先用 Pydantic v2 对 LangGraph 节点输入输出进行校验；只有在模型路由、Agent 单元测试、结构化输出等需求变得复杂时，再引入 PydanticAI，避免过早增加第二套 runtime。

参考：https://github.com/pydantic/pydantic-ai

### 3.2 图片生成与处理\n\n**首期决策：需要真实图像生成/编辑服务，但不需要 ComfyUI。** 产品能力需求与具体工作流引擎是两回事。先通过统一 Image Provider Adapter 调用一个可靠的云端图像模型 API，完成商品图二次改造、营销海报/信息图生成、局部修改等核心场景，并由自有后端负责素材版本、审核和任务状态。

| 项目/能力 | GitHub | 建议 |
|---|---|---|
| ComfyUI | https://github.com/Comfy-Org/ComfyUI | 作为可选的自托管图像/视频工作流执行后端，通过 API Adapter 调用 |
| Pillow | https://github.com/python-pillow/Pillow | 复用 IterWave 现有实践，做尺寸、格式、压缩、基础图像操作 |
| OpenCV | https://github.com/opencv/opencv | 复用基础图像处理、质量检测和视觉预处理能力 |
| 云端图像模型 | 由 Provider Adapter 接入 | 用于直接生成、局部编辑、背景替换等生产能力 |

图像服务必须抽象成统一接口，不允许业务流程直接依赖 ComfyUI 节点 ID 或某一家模型 API。首期先接云端图像 API。只有出现自托管模型、复杂多阶段节点编排、GPU 资源统一管理、数据不能出域，或经过测算确认自托管可显著降低成本/改善质量时，才启动 ComfyUI 评估。

建议接口能力：

- `generate_poster`：按策略和已审核文案生成营销图。
- `edit_product_image`：基于商家原图进行二次改造。
- `inpaint_region`：局部区域修改。
- `resize_for_channel`：渠道尺寸适配。
- `inspect_image`：分辨率、主体完整性、OCR/文字区域检查。
- `get_job_status`：异步任务状态、失败原因与产物地址。

**重要约束：** 原图永不覆盖；每次生成或编辑都形成新版本，保存 source_asset_id、指令、模型/工作流版本、参数摘要、生成时间和审核记录。商品外观、数量、规格、门店环境等真实信息不得被模型擅自改变。ComfyUI 的工作流、节点和模型可能各自有不同许可证，必须逐项检查，不能仅凭主仓库许可证推断整个模型链路可商用。

参考：https://github.com/Comfy-Org/ComfyUI\n\n**ComfyUI 引入门槛：** 至少满足上述一项明确业务/工程需求，并完成 GPU 运维、队列隔离、模型权重与自定义节点许可证、任务恢复和安全隔离评估；不能仅因为它流行或节点丰富就纳入首期架构。

### 3.3 浏览器自动化与渠道适配

Playwright 已在 IterWave 使用，建议继续复用，但严格拆分用途：

1. 自动化测试：完整覆盖商家端核心流程、刷新恢复、审核、上传和发布门控。
2. 只读采集：在目标平台规则与授权允许时采集公开或账号可见数据。
3. 草稿准备：在平台允许且账号授权有效的前提下，辅助填写内容、上传素材、保存草稿。
4. 最终发布：由商家确认；未经明确授权与产品规则允许，不得自动点击最终发布。

渠道 Adapter 负责平台差异，不允许在营销业务逻辑中散落平台专属选择器和字段。

参考：https://github.com/microsoft/playwright

### 3.4 自动化、任务队列与数据层\n\n**n8n 首期不引入。** 当前营销流程固定，系统需要的是稳定执行产品定义的业务步骤，而不是给运营人员提供任意自动化编排。FastAPI 服务直接调用模型、图像和渠道 Provider；通知、回调、重试、审计等由应用服务处理。未来若出现大量 SaaS 双向集成、跨系统事件路由或非核心后台自动化，再单独评估 n8n，并确保它不持有营销任务的权威状态。

| 能力 | 当前资产 | 建议 |
|---|---|---|
| 轻量定时 | APScheduler | 继续用于单实例调度；多实例部署前增加分布式锁/调度治理或替换 |
| 执行队列 | IterWave 全局队列/worker | 抽取任务接口、超时、隔离、重试、幂等和恢复设计 |
| 长流程恢复 | 尚需正式生产化 | LangGraph checkpoint 与业务任务表配合；不可只依赖内存状态 |
| 业务数据库 | SQLite | 原型阶段可保留；多门店 SaaS 生产优先 PostgreSQL |
| 文件存储 | 现有本地资产目录 | 生产迁移对象存储，使用不可变对象版本与受控访问 URL |
| 事件/通知 | 暂无统一方案 | 先通过应用事件接口解耦；需要大量外部集成时再引入 n8n |

不建议在第一阶段同时引入 Temporal、Celery、RQ、n8n 或 LangGraph 等多套执行系统。首期由自有业务状态机、持久化任务表和异步 Worker 协同完成流程；数据库负责业务事实。只有出现复杂 AI 子流程时再评估 LangGraph；出现跨服务、长时间运行、复杂补偿或高可靠定时需求时，再专项评估 Temporal 等 durable workflow 引擎。

## 4. 推荐目标架构

```text
商家端 React + TypeScript
          |
          v
       FastAPI
          |
          +--------------------+
          |                    |
          v                    v
   营销领域服务             素材/渠道 API
   - 门店上下文             - 图片 Provider Adapter
   - 商品/活动事实          - 平台 Channel Adapter
   - 审核与版本             - Playwright Worker
   - 质检规则
   - 发布门控
          |
          v
   LangGraph 执行编排
   - 需求理解
   - 机会/策略生成
   - 文案生成与整改
   - 图片生成与整改
   - 渠道适配
   - 质量检查
   - 等待商家确认 / 恢复
          |
          +-----------------------------+
          |              |              |
          v              v              v
      LLM Provider   Image Provider   External APIs
          |
          v
 PostgreSQL + Object Storage
          |
          +--> 任务/版本/审核/发布/审计
          +--> 图片原图与派生版本
          +--> 内容表现与经营指标
          +--> Agent checkpoint / 执行事件
```

### 4.1 必须坚持的分层边界

- **Agent 不拥有业务真相：** 模型可以提出策略和内容，不能自行修改价格、优惠、库存、审核结果或发布状态。
- **业务服务决定能否前进：** 每个阶段转换都通过服务端规则校验。
- **业务状态机是唯一主控：** 业务表保存任务、审核和发布的权威状态；AI 执行框架（未来如引入 LangGraph）只能管理子流程执行上下文，不能与业务表争夺状态所有权。
- **商家审核是显式中断：** 文案与图片分别等待审核；修改后只使真正依赖该版本的下游内容失效。
- **发布动作必须有幂等保护：** 使用发布请求 ID、内容包快照和平台返回 ID 防止重复发布。
- **效果数据必须有证据：** 保存来源、统计口径、同步时间、关联关系和归因可信度；没有交易数据不能推导营收或 ROI。

## 5. 核心营销流程与 Agent 节点建议

| 节点 | AI/规则职责 | 输出 | 是否需要商家确认 |
|---|---|---|---|
| 需求理解 | 提取目标、任务类型、商品、渠道和缺失信息 | Brief JSON | 信息不足时提问 |
| 经营上下文 | 查询门店、商品、活动、素材、历史数据 | Context Snapshot | 冲突事实需确认 |
| 机会/策略 | 热点匹配、客群分析、主题和渠道建议 | Strategy Version | **需要** |
| 文案生产 | 生成渠道文案、标题、话题和 CTA | Copy Version | **独立审核** |
| 图片生产 | 生成信息图或原图二次改造 | Image Version | **独立审核** |
| 渠道适配 | 结构、尺寸、平台字段与预览 | Channel Package | 最终汇总确认 |
| 质量检查 | 事实、优惠、文案、OCR、画幅和规则检查 | QC Report | 阻断项需处理 |
| 发布准备 | 草稿保存/人工发布准备、状态回读 | Publish Record | **最终发布确认** |
| 效果分析 | 汇总内容和经营指标、证据限制 | Effect Report | 由数据观察窗口决定，不在发布完成时立即生成 |

策略、文案、图片、渠道包、质检报告和发布包均需版本化。Agent 执行事件应记录 run_id、task_id、node、输入版本、输出版本、模型、耗时、token/费用、重试与错误摘要。

## 6. 分阶段实施路线

### P0：打通一条真实营销链路

1. 建立 FastAPI 服务骨架、配置与密钥管理。
2. 建立 Pydantic 业务模型：Brief、Strategy、Copy、ImageAsset、Review、ChannelPackage、QCReport、PublishRecord。
3. 用 Python 业务状态机和持久化任务表完成“需求理解 → 策略 → 文案生成 → 文案审核 → 图片生成 → 图片审核”的固定流程；验证暂停、恢复、重试和人工修改回路。
4. 先接一个真实 LLM Provider 和一个真实图像 Provider；全部通过 Adapter。
5. 原图上传、素材存储、版本记录与审核记录真实落库。
6. 商家端 Demo 改为调用 API；模拟能力明确标记，真实能力未接入时不得伪装成功。
7. 建立任务失败、重试、取消和恢复机制。

**P0 验收：** 同一营销任务可以暂停等待商家审核；用户修改意见后生成新版本；服务重启后可恢复；文案/图片审核状态独立；原图不被覆盖；所有产物能追溯来源。

### P1：渠道执行与安全

1. 选择一个首发渠道完成授权状态、草稿准备和结果回读。
2. Playwright 只用于平台允许的操作，增加超时、截图证据、幂等和人工接管。
3. 接入统一质量检查：商品事实、价格优惠、OCR、画幅、平台规则。
4. 建立多门店服务端授权、密钥托管、审计日志和文件访问控制。
5. 建立任务运行监控、模型调用记录和成本统计。

### P2：经营效果闭环

1. 接入可获得的内容表现数据。
2. 对接门店实际经营数据源（在业务确认来源与授权后）。
3. 建立内容、任务、账号、作品和经营指标之间的可审计关联。
4. 设计观察窗口、统计口径、归因可信度和数据缺失处理。
5. 基于有证据的结果更新门店画像与下一轮营销建议。

## 7. 不建议现在引入的东西

- **不要把 Dify 直接嵌成商家主工作台。** 它不是我们的产品 UI，也不能替代 v1.8 的审核、版本、门店权限和经营效果规则。
- **首期不要引入 n8n。** 固定营销流程由 FastAPI 和自有业务状态机直接执行；未来 n8n 仅考虑外围 SaaS 集成/事件路由，绝不持有核心业务状态。\n- **首期不要引入 ComfyUI。** 先用云端图像 API 和统一 Provider Adapter 实现生图/改图；只有自托管、复杂节点编排或成本/数据边界需求明确时再评估。\n- **不要把 LangGraph 当成固定流程的必选底座。** 先用 Python 状态机与任务服务；只有复杂 AI 子流程需要持久化编排、动态分支和中断恢复时再引入。
- **不要为了“多 Agent”而拆成一堆角色。** 首期以单一营销执行图为主，节点职责清晰；只有在并行任务或独立上下文确有收益时再拆子图/子 Agent。
- **不要同时上多套队列/工作流引擎。** 避免状态分散、重试重复和故障排查复杂。
- **不要把浏览器自动化当官方 API 的替代品。** 平台规则、账号授权和页面变化都会影响可靠性。
- **不要把图片生成框架等同于图像模型。** 工作流引擎、节点、权重模型、字体和素材都需要分别核查许可与商用权利。

## 8. 技术验证清单

正式锁定技术方案前，必须做一个可运行的纵向切片，而不是只比较文档或 Star 数：

- [ ] 自有业务状态机在服务重启后可从持久化任务/业务状态恢复，审核中断与修改回路可重复执行。\n- [ ] 只有当复杂 AI 子流程确有需要时，才额外验证 LangGraph checkpoint；它不是首期验收前置条件。
- [ ] 商家审核通过/要求修改两条分支可重复执行且不会重复生成发布记录。
- [ ] Pydantic 对模型结构化输出进行严格校验，错误可重试且保留原始输出。
- [ ] 同一任务重复请求具备幂等性。
- [ ] 图片原图、编辑版本、审核版本可追溯，无法覆盖原图。
- [ ] 图像 Provider 可替换，不改变营销业务层代码。
- [ ] Playwright 任务超时后可安全停止，平台端状态不明时转人工核验。
- [ ] 门店 A 无法读取门店 B 的任务、商品、素材、密钥和效果数据。
- [ ] Agent trace、模型费用、节点失败和人工决策可审计。
- [ ] 关键路径具备单元测试、集成测试和真实浏览器 E2E。

## 10. 最终建议

**当前最合理的技术组合：**

- 产品：保留 Smart-Marketing 的自有交互和 v1.8 业务规则。
- 后端：从 IterWave 抽取 FastAPI、Pydantic、migration、worker、Playwright、图像处理实践。
- AI：引入 LangGraph，作为营销执行流程的编排 runtime。
- 图片：抽象 Provider Adapter，先接一个真实服务，再按成本/效果扩展 ComfyUI 或其他模型。
- 数据：先把业务状态、审核版本、执行 checkpoint 和素材元数据分开设计；生产数据库优先 PostgreSQL。
- 外部自动化：首期不引入 n8n；未来仅用于外围 SaaS 集成、事件路由和通知，不进入核心业务状态机。
- 效果闭环：独立建设数据采集、证据与归因能力，不把内容曝光等同于经营增长。

这条路线既能最大化复用现有代码，也能避免把产品做成通用低代码平台或 ERP。选型原则是：**固定流程用自有代码控制；智能判断交给模型；图像能力通过 Provider 接入；只有复杂度真实出现时才增加编排框架。先做出一条可以真实执行、可以暂停恢复、可以审计、可以由商家控制的营销链路，再扩展技术组件。**
