## 1. 结论摘要

IterWave 的主要价值不是某个单独的文案/图片功能，而是已经沉淀出一套内容运营执行底座：持久化任务队列、任务状态与版本、平台能力适配、草稿保存边界、失败恢复、数据采集与证据化分析。

这些能力与 AI 门店运营官的“按需提出经营目标—AI 完整执行营销—商家确认关键事实与发布—基于数据验证经营效果”链路高度相关。建议采用**分层复用、按产品边界裁剪**，不建议把 IterWave 整个产品或其账号运营模式并入门店端。

本次审查仅能确认 GitHub 账号当前可访问的三个仓库。未发现该账号下其他相关仓库；这不代表账号之外或未授权组织内不存在其他项目。

### 3.2 可借鉴但必须裁剪

| IterWave 能力 | 不直接照搬的原因 | 门店运营官的改造方向 |
|---|---|---|
| 总体计划、平台子计划、长期排期 | 门店产品定位是按需制作，不应让商家管理内容排期和复杂计划 | 内部保留策略快照与执行依赖；界面只呈现当前营销目标、成果和待确认事项 |
| 自动开启下一轮内容生产 | 自动循环容易偏离门店即时经营目标，也可能制造无效内容 | 仅在经营效果有足够样本与证据后，向商家提出下一轮建议；由商家发起 |
| 多账号组/租户隔离模型 | IterWave 的账号组不等于门店业务模型；Smart-Marketing v1.8 不建立租户层级 | 采用 Store/StoreUser 的门店归属和服务端授权，不引入账号组 UI 或独立租户管理 |
| 平台评论、回复、关注等主动运营 | 与首期营销交付无关，平台规则及账号风险高 | 首期不迁移；不做自动评论、关注、私信等动作 |
| 基于 Playwright 的平台页面自动化 | 平台 DOM/选择器易变，真实授权、验证码和风控限制复杂 | 仅用于商家本人授权的只读采集（D-01 路径 A，见 `docs/FRAMEWORK_SELECTION_AND_REUSE.md` §2.4）与 E2E；官方 API 优先，始终保留人工发布确认。 |
| 账号运营节奏、配额与定时任务 | 不应把门店端变成账号运维控制台 | 只保留后台任务限流、重试、熔断和资源配额，隐藏实现复杂度 |

## 4. 明确不建议迁移的内容

1. IterWave 面向创作者的账号定位、选题库、内容轮次与长期计划管理 UI。
2. 自动评论、自动回复、自动关注等主动账号运营动作。
3. 未经门店经营数据验证的“自生长”自动营销闭环。
4. 将平台账号组直接映射成门店/租户的数据库与权限设计。
5. 依赖脆弱 DOM 选择器的页面自动化作为首期关键链路。
6. IterWave 的整套前端页面与导航结构。

## 6. 推荐目标架构

坚持门店端“按需制作、交付物优先”，复杂度留在服务端。

```text
门店 Web / 管理端
       |
       v
业务 API 与门店权限上下文
       |
       +---- 营销编排服务（需求、策略、审核、发布门槛）
       |
       +---- AI 能力网关（文本模型 / 图像模型 / OCR）
       |
       +---- 资产服务（门店资料、素材、文案/图片版本）
       |
       +---- 持久化任务队列与 Worker
       |          |
       |          +---- 文案/策略任务
       |          +---- 图片生成/编辑任务
       |          +---- 渠道适配与质检任务
       |          +---- 发布草稿任务
       |          +---- 指标采集任务
       |
       +---- 渠道适配器（授权、草稿、只读数据读取）
       |
       +---- 经营效果分析（内容表现、意向、经营结果、归因可信度）
       |
       +---- 审计、成本、熔断与人工恢复
```

建议统一的核心对象：

- `Store`、`StoreUser`：门店与用户归属。
- `MarketingTask`：用户发起的一次营销需求。
- `StrategySnapshot`：已确认的策略与经营事实快照。
- `ArtifactVersion`：文案、图片、渠道内容等不可变版本。
- `ReviewRecord`：文案/图片独立审核记录。
- `QualityReport`：规则/模型质检结果及版本。
- `PublishPackage`：最终冻结的内容包与商家确认。
- `ChannelAccount`、`ChannelOperation`：授权账号及外部操作记录。
- `MetricObservation`：有来源、有周期、有口径的指标观测。
- `Job`、`AuditEvent`：异步任务与可追溯审计事件。

所有业务对象必须带 `store_id`；服务端每次请求都从已认证身份解析门店权限，不能信任前端传入的 store_id 作为授权依据。

## 7. 分阶段实施建议

### P0：先建立可靠执行底座

1. 将 Smart-Marketing 当前纯前端 Demo 的能力边界保持清晰；新增生产后端，不把 localStorage 当作生产数据层。
2. 建立 Store/StoreUser 服务端身份与数据访问边界。
3. 建立关系型数据库及版本化迁移；为任务、资产、审核、质检、发布包、指标和审计建立数据模型。
4. 建立持久化异步队列、Worker、幂等键、超时、进度、失败状态和人工恢复。
5. 建立模型 Provider 抽象与调用审计；模型不可用时明确失败，不伪装为真实 AI 结果。
6. 建立文案/图片独立版本与审核状态机；策略或事实变更使相关下游版本失效。
7. 建立图片资产服务：原图不可覆盖、版本可追溯、文件与像素限制、OCR/质量检查接口。
8. 将 AI 调用成本、任务日志、错误脱敏和密钥引用纳入平台管理端。

### P1：接入真实渠道与热点

1. 先接入热点源适配、来源追踪、去重和门店匹配。
2. 定义平台能力矩阵：授权、读取、草稿保存、发布、指标读取分别标明支持/未支持/待验证。
3. 优先验证官方 API；页面自动化仅作为受控备选方案。
4. 采用草稿保存与发布动作分离的安全设计；发布必须由商家确认。
5. 采集作品 ID、URL、账号 ID 和平台返回证据；不确定的操作结果进入待核实状态。
6. 建立限流、熔断、登录失效检测和只读恢复探测。

### P2：经营效果与反馈优化

1. 先统一内容表现指标的来源、周期、口径、完整性与更新时间。
2. 再接入可验证的咨询、到店、订单、销售额、优惠券核销数据。
3. 样本不足时只显示数据积累中，不输出结论；未知值不补零。
4. 对内容主题、渠道、时段、素材和 CTA 做分层分析，显示样本量和归因限制。
5. 将分析结果转成下一次营销的建议，不默认自动创建营销任务。

## 9. 本轮决策

- **采纳**：持久化任务队列、显式状态机、版本快照/依赖失效、幂等与审计、任务恢复、Provider/Adapter 抽象、指标证据模型、熔断与安全边界。
- **复用优先级**：本地 Easel 实现 > IterWave 派生实现 > 自研。解析、匹配、聚合、走势、归因口径和前端展示一律优先复用，不以“架构不同”为由重写；平台采集通道按 D-01 路径 A 的授权边界处理。
- **改造后采纳**：热点发现、平台草稿保存、账号健康检查、渠道指标分析；实现优先复用 Easel（映射见 `docs/FRAMEWORK_SELECTION_AND_REUSE.md` §2.3）。
- **暂缓**：跨平台定时排期、自动下一轮营销；平台页面自动化仅限商家授权只读采集（D-01 路径 A）。
- **不采纳**：自动评论/关注等主动运营、创作者账号组模型、复杂计划管理 UI。
- **产品原则不变**：AI 门店运营官仍是按需工作的完整营销执行官；商家只处理关键事实、内容审核和发布确认；经营效果必须基于真实数据与可解释证据。
