# AI 门店运营官 — UI/UX 审查与产品边界修订

审查日期：2026-11-10  
对应产品基线：[PRODUCT_DESIGN.md v1.6](PRODUCT_DESIGN.md)  
对应验收矩阵：[DEMO_ACCEPTANCE_MATRIX.md v1.3](DEMO_ACCEPTANCE_MATRIX.md)

> 本文是当前有效的产品审查结论。此前版本中未经确认的 SaaS 管理模块和外部系统集成建议已废止，不得继续作为开发依据。

## 一、审查结论

当前产品必须坚持“AI 门店运营官”定位：商家按需提出营销目标，AI 完整执行营销，并在数据可用后验证经营效果。产品不是 ERP、POS、CRM、数据中台或通用 SaaS 运维后台。

此前文档与 Demo 出现了范围扩张和前后矛盾：
- 产品设计前文保留热点发现与匹配，后续页面清单却没有热点机会入口，验收矩阵还将热点写成未接入能力。
- 管理端引入租户、角色、工单、素材审核、渠道连接、数据接入和独立归因配置，均超出已确认范围。
- 用户管理被独立成模块，没有放在门店管理中。
- 任务监控和 AI 运行记录重复拆分，未围绕营销任务的完整执行过程组织。
- 模型配置未按门店隔离，无法满足不同门店使用不同供应商和 API Key 的要求。
- 营销任务流程条与实际页面 Tab 不匹配，需求理解缺少独立工作页面。
- 门店档案已有内部导航/面包屑时，外层重复导航造成视觉冗余。

以上均属于产品设计偏移，需在产品文档、验收标准和 Demo 中统一修正。

## 二、正确的核心业务结构

### 2.1 门店端

1. **AI 营销**：需求理解、热点机会、策略确认、文案工作室、图片工作室、渠道适配、质量检查、发布确认。
2. **营销任务**：查看执行状态、审核事项、整改历史、发布状态和失败恢复。
3. **经营效果**：独立分析发布后的内容表现和经营指标，展示数据来源、时间、口径与可信度。
4. **门店资料**：门店档案、商品与服务、活动优惠、品牌规范、客群与经营、知识库、素材库、渠道账号。

### 2.2 平台管理端

1. 运营总览。
2. 门店管理（门店档案、门店用户、门店级模型配置）。
3. AI 运行监控（营销任务执行轨迹及其下钻 AI 调用记录）。
4. AI 能力配置（模型目录、提示词、平台级能力）。
5. 用量与成本。
6. 审计日志与必要系统配置。

明确删除：租户管理、独立用户管理、角色管理、工单、后台素材审核、后台渠道连接、POS/团购/CRM/会员数据接入管理、独立归因与数据质量后台。

## 三、热点采集与匹配：必须恢复的核心能力

热点能力不是普通资讯列表，也不是要求商家自己浏览海量热搜。系统应主动采集可用热点，并完成筛选、匹配和营销转化。

**核心流程**

1. **热点采集**：采集与门店营销相关的公开趋势信息，包括本地热点、平台趋势、节日节气、天气季节、区域活动和行业话题。每条热点记录来源、采集时间、地域、有效期和可用状态。
2. **清洗与筛选**：去重，识别地域与行业，判断时效；过滤过期、无来源、风险过高或与门店经营明显无关的内容。
3. **门店匹配**：结合门店行业、位置、客群、商品/服务、活动、品牌规范、经营限制和当前营销目标评估相关性。
4. **机会排序**：说明匹配商品、匹配客群、匹配场景、适合渠道、时效窗口、风险和推荐理由。排序依据必须可解释，不以热度单一指标决定。
5. **内容营销建议**：对匹配热点给出内容切入角度、标题/主题方向、内容形式、推荐渠道、所需素材和行动引导。
6. **商家选择**：商家可采纳、忽略、暂缓或要求调整；采纳后进入营销任务，热点来源和匹配快照随任务留存。
7. **效果回流**：任务发布并积累到可用数据后，评估该热点内容的表现，沉淀适合该门店的热点类型与内容经验。

**界面要求**
- AI 营销工作台有“适合本店的热点机会”区域，可显示推荐热点、匹配商品/场景、推荐理由、有效期和来源。
- 热点详情展示原始来源摘要、采集时间、地域、热度/趋势信号（仅在来源提供时展示）、匹配解释、风险提示和内容建议。
- “基于此热点创建营销”必须创建真实营销任务并携带热点引用；不能只是展示卡片或跳转空白页。
- 无匹配热点时显示“当前没有适合本店的热点”，同时提供常规营销入口；不能强行推荐。
- 热点采集源不可用时明确显示未连接/最后成功时间/失败原因，不得用静态假热点冒充实时采集。
- 纯文案、纯图片等不依赖热点的任务允许跳过热点步骤，并记录原因。

## 四、营销任务流程与页面一致性

流程顺序：
1. 需求理解
2. 热点机会（适用时；可跳过并说明原因）
3. 策略确认
4. 文案工作室与独立审核
5. 图片工作室与独立审核
6. 渠道适配
7. 质量检查
8. 发布确认

要求：
- 流程条中的每个步骤必须有对应页面或明确的可跳过状态。
- 需求理解必须是可操作页面，展示 AI 结构化提取的目标、任务类型、商品、客群、渠道、时间、限制和待补充信息。
- 热点机会必须能查看、选择或跳过；不能只在策略说明中出现“外部热点未连接”。
- 策略确认必须展示策略依据、热点匹配结果（若适用）、目标客群、商品卖点、内容主题、渠道理由、活动建议、素材和风险。
- 文案与图片分别审核、分别整改、分别保留版本。
- 效果复盘是独立模块，不是任务发布后的自动步骤。

## 五、门店资料与导航

- 门店资料只保留 AI 营销所需信息，不增加未经确认的外部业务系统。
- 门店档案页面内部已有分区导航/面包屑时，外层顶部不再重复展示同一层级导航；顶部只保留必要的页面标题、全局操作和用户入口。
- 门店用户在平台管理端的“门店管理 → 门店详情 → 用户”中维护，不设置独立用户管理一级菜单。
- 渠道账号属于门店资料，由门店绑定和维护。
- 不默认提供 POS、团购核销、会员 CRM 等连接器。

## 六、模型与密钥边界

- 模型使用配置必须绑定门店。
- 每家门店可配置独立供应商、模型、API 地址和 API Key；文案、图片等能力可使用不同模型。
- 管理员从门店详情进入配置，不设置一个全局共享 API Key 的默认模型路由。
- 平台可维护可选模型目录与能力兼容信息。
- 真实 API Key 必须服务端加密托管；浏览器端只显示掩码与配置状态。当前纯前端 Demo 只能演示字段和状态，不能声称已实现安全密钥托管。

## 七、AI 运行监控

任务监控与 AI 运行记录合并，不再是两个并列菜单。

- 一级列表按门店、营销任务、任务状态、时间和异常筛选。
- 任务详情展示需求理解、热点匹配、策略、文案、图片、质检和发布等业务节点的进度。
- 每个节点下钻展示对应 AI 调用：能力、模型、排队/执行状态、耗时、重试、错误摘要和成本（若可用）。
- 排队只是 AI 调用生命周期的一种状态。模块目标是回答“营销任务执行到哪里、为什么卡住、AI 是否完成工作”，而不是单纯展示 API 队列。
- 不重复统计任务数与调用数；业务任务和技术调用必须区分层级。

## 八、经营效果

- 经营效果独立于营销任务。
- 只展示真实采集或明确标记的人工录入/演示数据。
- 每项指标展示来源、更新时间、统计周期、统计口径和可信度。
- 没有数据源时显示空状态；没有匹配交易数据时不虚构到店、订单、核销和 ROI。
- 数据质量提示和归因限制作为效果页面的解释信息，不建设独立后台归因模块。
- 不默认假设 POS、CRM、会员或团购核销系统已接入。

## 九、实施与验收红线

1. 先按本文及产品设计基线修正页面地图、流程、字段和验收矩阵，再开发。
2. 每个导航、Tab、流程步骤必须有真实页面或明确状态；禁止流程条与页面不一致。
3. 每个按钮必须完成导航、状态变化或明确告知未接入原因。
4. 热点必须有采集来源、时间、时效、匹配理由和“基于热点创建营销任务”的完整链路；没有真实采集服务时只能清楚展示模拟状态。
5. 不得擅自加入 POS、团购、CRM、会员等外部系统。
6. 不得出现租户、角色、工单等未经确认的业务模块。
7. 门店用户必须归属于门店；模型与密钥必须按门店隔离。
8. 代码语法检查不等于浏览器验收；未实测的项目必须标注待验收。
