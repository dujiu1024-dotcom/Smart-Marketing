# AI 门店运营官 — UI/UX 审查与整改基线

> 文档版本：v1.8  
> 对应产品基线：[PRODUCT_DESIGN.md v1.8](PRODUCT_DESIGN.md)  
> 对应验收矩阵：[DEMO_ACCEPTANCE_MATRIX.md v1.8](DEMO_ACCEPTANCE_MATRIX.md)  
> 更新日期：2026-11-10

本文是 v1.8 产品基线下的现行 UI/UX 规则。历史轮次中的产品范围、页面结构和验收状态不再作为当前依据。

## 1. 审查结论

产品应保持“AI 门店运营官”定位：商家按需提出目标，AI 完成营销执行，商家确认关键事实与发布，系统在数据可用后评估效果。门店端不是 ERP；平台管理端不承担门店日常营销运营。

当前 Demo 已具备主要页面和部分本地交互，但仍有三类风险：
- 页面、入口和任务状态机尚未完全统一。
- AI 模拟能力容易被误认为真实模型能力。
- 大型模板字符串和单文件逻辑增加维护成本；真实浏览器 E2E、视觉回归和可访问性验收尚未完成。

## 2. 唯一信息架构

### 2.1 门店端

| 一级入口 | 职责 | 关键内容 |
|---|---|---|
| AI 营销 | 按需发起营销与发现机会 | 自然语言制作、AI 推荐营销/热点机会、策略与内容制作工作区 |
| 营销任务 | 跟踪执行过程 | 任务列表、需求与策略确认、文案/图片审核、渠道适配、质检、发布状态 |
| 账号运营监测 | 维护账号连接状态与作品登记 | 授权状态、账号可用性、作品登记、归属核验、同步状态 |
| 经营效果 | 分析内容表现与经营结果 | 已归属作品表现、经营指标、数据来源、统计口径、可信度与建议 |
| 门店资料 | 维护营销所需事实 | 门店档案、商品服务、活动优惠、品牌规范、客群经营、知识、素材、渠道账号 |

**账号运营监测与经营效果的边界**
- 账号运营监测回答：“账号是否可用？授权是否有效？作品是否已登记？归属核验和数据同步处于什么状态？”
- 经营效果回答：“已确认归属的作品表现如何？是否有可信的经营结果数据？数据口径和归因限制是什么？”
- 两处可以引用同一作品记录，但不能重复制造指标口径。账号健康状态不等于营销效果。

### 2.2 平台管理端

只包含运营总览、门店管理、AI 运行监控、AI 能力/提示词配置、用量与成本、审计日志和系统配置。门店列表进入门店详情；门店用户和门店级模型配置位于门店详情内。

不增加租户、独立角色、工单、后台素材审核、门店经营资料编辑、POS/CRM/会员连接管理或独立归因后台。

## 3. 首页入口与主路径

首页应让首次使用者明确知道从哪里开始：
1. 主入口“AI 推荐营销”进入热点机会发现，解决“我不知道做什么”的问题。
2. 次入口“按需制作”接受自然语言目标，解决“我已经知道要做什么”的问题。
3. “营销任务”只承接已创建任务，不重复提供新建入口。
4. 快速开始只作为按需制作的快捷模板，不得与主入口争夺同等视觉权重。

两个发起入口必须说明适用场景，不能让商家误以为需要先做热点推荐才能制作营销。

## 4. 营销流程与状态机

产品完整链路：

**需求理解 →（热点机会：适用时采纳或跳过并记录原因）→ 策略确认 → 文案审核 → 图片审核 → 渠道适配 → 质检 → 发布确认**

交互要求：
- 每个流程节点都有可访问页面、完成状态、阻断原因或明确的跳过状态。
- 流程条和 Tab 使用同一状态来源；不能各自维护互相矛盾的状态。
- Tab 可用于查看阻断说明，但查看页面不代表解锁业务动作。
- 需求未确认不得进入后续执行；策略未确认不得开始文案、图片、渠道、质检和发布。
- 跳过仅适用于不适用的节点，必须记录原因、操作者和时间；商家审核、事实确认和最终发布确认不得跳过。
- 修改需求或策略后，必须使依赖它的下游版本、审核或质检状态失效，并要求重新确认。
- 发布包必须冻结需求/策略快照、文案、图片、渠道内容、质检结果和商家最终确认。

当前代码已有需求/策略门控与发布校验逻辑；完整状态机（特别是热点节点的可跳过记录、统一进度计算及刷新恢复）仍需按验收矩阵验证和补齐。

## 5. AI 能力真实性与界面标识

所有 AI 产出页面必须在产出区域附近显示醒目的能力状态，不能只依赖页面顶部统一 Demo 标签。

推荐统一文案：
- 文本类：**演示模拟｜当前为本地规则/预置内容，不是真实大模型生成结果。**
- 图片类：**演示模拟｜当前为 SVG/占位预览，不是真实 AI 生图或图片编辑结果。**
- 热点类：**演示数据｜非实时采集，来源和更新时间以页面标识为准。**
- 渠道类：**本地预览｜不代表平台官方规格校验或真实发布。**

至少覆盖需求理解、策略、文案生成/整改、图片生成/整改、热点推荐、质检和渠道适配。用户上传的真实内容、商家手工编辑内容与系统模拟产出必须区分来源。

## 6. 作品归属、账号监测与经营效果

- 本系统发布记录应保存任务 ID、冻结内容包 ID、平台账号 ID、平台作品 ID、URL、发布时间及平台响应。
- 通过官方授权接口读取作品时，必须核验账号和作品的可靠标识。
- 商家人工登记的作品先标记待核验；不能仅凭 URL、标题或内容相似度认定为系统发布。
- 未核验作品不得计入具体任务的正式效果。
- 每项指标显示来源、同步时间、周期、口径和真实性状态。
- 播放、阅读和互动不等于订单、到店或营收；缺少交易证据时不得输出 ROI 或经营增长结论。

## 7. 多门店上下文与数据安全提示

- 门店端所有任务、商品、活动、素材、渠道和效果数据必须始终绑定当前门店。
- 切换门店后，页面列表、详情、统计、表单和 AI 上下文必须同步切换。
- 无当前门店或门店数据为空时，显示明确空状态，不回退展示其他门店数据。
- Demo 的 localStorage 命名空间隔离只用于模拟；界面和文档不得暗示其等同于生产级权限隔离。
- API Key 仅允许展示安全引用/掩码状态；当前 Demo 不保存真实密钥。

## 8. 可访问性与响应式要求

- 所有交互控件可通过键盘访问，焦点样式清晰。
- Tab 使用 `role=tablist/tab`、`aria-selected`，面板应有可读名称；动态提示使用适当的 live region。
- 表单字段必须有可关联标签；错误、阻断和成功反馈不能只依赖颜色。
- 表格窄屏允许横向滚动，关键操作不能被裁切。
- 页面主操作优先级明确；移动端主操作不能被挤出可视区域。
- 空状态必须说明“为什么为空”和“下一步能做什么”。

## 9. 工程可维护性要求

- 将页面渲染拆成职责清晰的小函数/组件；优先按业务域拆分，不再继续扩张单个巨型 `app.js`。
- 将业务状态计算、事件处理和 HTML 展示分离，避免在巨型模板字符串中嵌套复杂规则。
- 删除重复映射、重复事件监听和失效分支；导航标题映射必须唯一。
- 每次拆分必须保持现有业务行为，并补充路由、状态和持久化回归检查。
- 不能为追求文件拆分而一次性重写全部业务逻辑；采用可验证的小步重构。

## 10. 验收原则

状态必须分为：
1. **代码已实现**：代码路径存在，不代表执行正确。
2. **静态检查通过**：语法、静态规则或 mock 测试通过，不代表真实浏览器通过。
3. **浏览器实测通过**：在真实浏览器执行指定路径并记录结果。
4. **生产服务已接入**：真实 API、授权和服务端安全已联调，不等同于 Demo 本地模拟。

没有浏览器证据的项目不得标记为浏览器通过。当前 Demo 尚未完成真实浏览器端到端验收。


## 11. P1/P2 本轮实施说明（2026-11-10）

- 首页入口调整为“AI 推荐营销”主入口与“按需制作”次入口；目标模板仅预填，不直接创建任务。
- 热点机会决策放入策略确认页：采纳已关联热点，或记录不使用热点的原因。决策纳入策略快照和质检指纹，变更后下游确认失效。
- 保持七个主要任务页签；热点决策是策略确认页内的必填判断，不另增孤立页签。
- 任务工作区渲染与本地校验规则拆分至 demo/task-renderers.js；经营效果页面渲染拆分至 demo/effect-renderers.js，门店资料页面渲染拆分至 demo/store-renderers.js。
- 任务与门店资料 Tab 增加 tabpanel 关联和方向键/Home/End 键盘操作；通用表单 helper 增加 label/id 关联。
- schema v10 为历史任务补充默认门店归属，避免无归属任务在门店过滤时重复出现。当前仍未提供完整门店资料切换和服务端隔离。
- 真实浏览器、移动端、屏幕阅读器验收仍未完成。

- 首页「发现适合本店的营销机会」入口压缩为紧凑推荐卡片，标题字号、行高、内边距和辅助说明均收敛；目标是在桌面端控制为一至两行标题，移动端避免形成过高首屏模块。

- 当前为代码层实现，尚未完成真实浏览器视觉回归；需检查窄屏换行、编辑页滚动、返回导航和新版本保存后状态。


## UI/UX v2 整改实施记录（2026-11-10）

- 首页收敛为 AI 推荐营销主入口、当前门店任务状态和按需制作次入口；复杂目标表单迁移至独立「按需制作」页面。
- 营销任务详情移除重复七步进度条，保留单一 Tab 导航，并在步骤项内显示完成/当前/待处理状态。

- 门店档案中的经营画像字段不再重复编辑；品牌定位与差异化归品牌规范维护，客群、场景和经营目标归客群与经营维护。
